=== Q1 | domain: Understanding Requirements | pick: 1 ===
A stakeholder says 'the bot should understand customer intent.' Before building anything, what is the right next step?
A) Translate this into concrete functional requirements: which intents, what fields to extract, and what counts as a correct classification
B) Start building immediately and let the model's general capability handle whatever 'intent' turns out to mean
C) Pick the largest model so intent understanding is as strong as possible regardless of scope

Why: Vague business language must become checkable functional requirements before design starts. Building first, oversizing the model, or reverse-engineering requirements from a prompt all skip the step that makes the system buildable and testable.

=== Q7 | domain: Claude API Mechanics | pick: 1 ===

=== Q29 | domain: Context Engineering | pick: 1 ===
Two independent subagents each need a large shared reference document to complete their separate parts of a task, but the documents should not pollute each other's follow-up reasoning with the other's intermediate steps.
A) Give each subagent its own isolated context containing the shared reference, so their intermediate reasoning never crosses over
B) Run both subagents in a single shared context so they can see each other's reasoning as it happens
C) Give the reference document to only one subagent and have it verbally summarise the whole thing to the other
D) Skip giving the document to either and let both reason from general knowledge instead

Why: Context isolation through separate subagent contexts lets each hold the shared reference without their intermediate reasoning bleeding together.
